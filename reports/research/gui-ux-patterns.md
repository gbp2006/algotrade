# Паттерны UX внешних торговых интерфейсов — что применить к нашему UI

Дата: 2026-11-24. Режим: только исследование (код, конфиги и сервисы не менялись).
Задача: где живут позиции/заявки/риск, как один экран показывает много роботов, как группируются
инструменты по типу, что применить к нашим 4 разделам, что НЕ копировать, как убрать техшум.
Наложение делается на `web/templates/{trade,robots,accounts,health,index}.html`.

## 2. Факты по интерфейсам

### Kraken Pro
- Панели (график, стакан, ордера, позиции) можно отсоединять и переставлять; есть сброс к умолчанию.
- Вместо одной огромной таблицы — горизонтальная лента вкладок: Balances, Positions, Open orders,
  Conditional orders, Portfolio, Closed orders, Trades.
- Вывод: сначала **хороший дефолт**, потом кастомизация + сохранение + кнопка «сбросить».

### TradingView
- График — центр композиции; слева инструменты, справа watchlist; края интерфейса постоянны.
- Watchlist группируется по классу актива и сворачивается; symbol → котировка → нарратив = 3 zoom-уровня.
- Нет «гамбургер-меню» как единственного входа: навигация всегда видна.

### Binance
- Пять живых регионов: график, стакан, лента сделок, форма ордера, список открытых ордеров.
- Красный/зелёный зарезервированы за направлением (buy/sell, рост/падение); вторая размерность —
  заливка кумулятивного объёма в стакане, а не новый цвет.
- Вывод: цвет — дефицитный ресурс, его не тратят на «просто подсветить строку».

### OKX
- Формы покупки и продажи стоят **рядом**, а не переключаются тумблером: меньше ошибок, чем у
  подтверждающего диалога, потому что обе альтернативы видимы одновременно.
- Есть слайдер «% депозита» и быстрые доли (25/50/75/100).

### Interactive Brokers TWS
- Mosaic: рабочее место из плиток; вкладки рабочих пространств (workspace tabs).
- Отдельные панели Portfolio / Orders / Trades / Activity; Risk Navigator — отдельный риск-обзор.
- Вывод: риск — отдельный first-class экран, а не колонка в таблице позиций.

### Т-Инвестиции
- Виджетный workspace; 3 вкладки по умолчанию: Портфель / Что купить / Торговля.
- Портфель и «Активные заявки» рядом; по позиции — контекстное меню (закрыть, переставить).
- Вывод: «где мои деньги» и «что уже висит на рынке» — соседние вкладки, не разные страницы.

### Finam / FinamTrade
- Позиционирование «все инвестиции в одном месте»; пользователь сам собирает набор виджетов.
- Единый контроль портфеля вместо разрозненных экранов по типам активов.

### OsEngine
- Набор приложений: BotStation (роботы), OsTester, OsOptimizer, Miner (данные).
- Общий журнал, отдельный риск-менеджер, виртуальные позиции для paper-режима.
- Вывод: журнал и риск вынесены из карточки робота — это инфраструктура, а не свойство одного бота.

### 2026 dashboard patterns
- Fortress: закреплённая полоса из 3–4 чисел вверху + сравнительные панели (Benchmark, P&L, Drawdown).
- Vault: сравнение с бенчмарком обязательно; «Абсолютное число без сравнения мало что значит».
- Heatmap: нейтральная середина (не белая), подписи деградируют аккуратно при нехватке места.
- Fleet/mission-control (гипотеза): баннер общего статуса, карточки по убыванию тяжести, причина
  деградации прямо в карточке, master-list + массовые действия, тяжёлые вкладки грузятся лениво,
  все состояния роботов описаны одним словарём.

### Progressive disclosure (NN/g)
- Раскрывать по конкретной подписи («Показать 12 отклонений»), а не по «Ещё».
- Не скрывать то, что нужно для сравнения вариантов или для безопасности.

## 3. Ответы на вопросы

**Где живут позиции/заявки/риск.** У всех — рядом и одновременно: лента вкладок в Kraken
(Balances/Positions/Orders), соседние панели в TWS (Portfolio/Orders/Activity) и Т-Инвестициях
(Портфель/Активные заявки). Риск — отдельный first-class вид (Risk Navigator в IB, риск-менеджер в
OsEngine), а не поле в карточке. У нас сейчас это размазано: позиции и заявки — в `trade.html`
(строки `s.position`, `o.status`), «риск» как такового нет, есть только `last_decision` и `counts`.

**Как один экран показывает состояние многих роботов.** Не одна таблица со всеми колонками, а
уровни: (1) закреплённая полоса KPI, (2) master-list, отсортированная по тяжести, (3) карточка с
причиной деградации inline, (4) lazy-детали. Единый словарь состояний (7 состояний — одним языком).
У нас в `robots.html` — плоский список с raw-бейджами `active/draft/paused/stopped/archived` без
сортировки по тяжести и без объяснения, почему робот не торгует.

**Как группируются инструменты по типу.** Валюта/индексы/акции/сырьё/фонды — сворачиваемые группы в
watchlist (TradingView), а не плоский выпадающий список. Группа = фильтр + счётчик + ленивое раскрытие.
У нас `by_type` и `spec_id=money_market` есть в данных, но в UI это либо `JSON.stringify(r.by_type)`,
либо raw `spec_id` — то есть группировка есть в модели, а в интерфейсе её нет.

**Какие паттерны применимы к нашим 4 разделам.** См. таблицу ниже и §5: KPI-полоса + лента вкладок
в Торговле, master-list с сортировкой по тяжести в Роботах, Comparative panels в Счетах,
баннер статуса + ranked exception queue в Здоровье; везде — единый словарь состояний и отказ от raw JSON.

**Что НЕ стоит копировать и почему.** Отсоединяемые панели Kraken без дефолта и сброса, кастомный
workspace TWS без «сбросить», цветовую кодировку Binance для подсветки строк, тумблер buy/sell вместо
двух форм OKX, heatmap без нейтральной середины, «Ещё…» вместо конкретной подписи, 7 разных слов для
одного состояния. Причины: теряется воспроизводимость экрана, цвет перестаёт значить направление,
растёт риск ошибочной заявки, теряется сравнение и безопасная информация.

**Как сделать интерфейс человекочитаемым.** Перевести модель в язык пользователя: id → имя +
вторичный мелкий id; `ORDER_STATUS_*` и `active/draft` → «Исполняется», «Черновик», «На паузе»;
`JSON.stringify` → счётчики и подписи; `code=k=v` → именованные параметры; `last_decision` → «Решение:
продать 3 Si по 105 000»; сырой `source` → «Источник данных: p-base (бумажный)».

## 4. Таблица: паттерн → куда применить → риск

| Паттерн | Куда применить у нас | Риск / ограничение |
|---|---|---|
| Закреплённая KPI-полоса из 3–4 чисел | `trade.html`, `health.html` (справа вверху) | При росте >4 чисел полоса превращается в шум; оставить 3–4 |
| Лента вкладок Balances/Positions/Orders | `trade.html`: объединить разрозненные таблицы | Нужно сохранять выбранную вкладку, иначе сброс при перезагрузке |
| Риск отдельным видом (Risk Navigator) | Новый блок в `trade.html` рядом с позициями | Не делать «риск = ещё одна колонка», иначе его не заметят |
| Master-list + сортировка по тяжести | `robots.html` (список инстансов) | Нужен единый ранг состояний, иначе порядок субъективен |
| Причина деградации inline в карточке | `robots.html`, `health.html` (вместо чистого `status`) | Текст причины может быть длинным — обрезать с «подробнее» |
| Единый словарь из ~7 состояний | Все 4 раздела (`status`, `badge`, `st`) | Требует маппинга на сервере, иначе рассинхрон с API |
| Группы инструментов по типу (сворачиваемые) | `robots.html` вместо `JSON.stringify(r.by_type)` | Скрытая группа может потерять счётчик — показывать число всегда |
| Две формы buy/sell рядом, %-слайдер | Форма ордера в `trade.html` | Требует больше места; на узком экране — стек, но обе видимы |
| Резерв красного/зелёного за направлением | Все таблицы с P&L и side | Подсветка строк другими цветами ломает семантику |
| Comparative panels / бенчмарк | `accounts.html` (портфель vs бенчмарк/депозит) | Без бенчмарка абсолютное число бессмысленно |
| Контекстное меню по позиции | `trade.html` (закрыть, переставить заявку) | Не заменять им явные кнопки для пользователя |
| Конкретная подпись «Показать N» вместо «Ещё» | Все раскрывающиеся блоки | «Ещё» дешевле, но скрывает объём и сравнение |
| Lazy-загрузка тяжёлых вкладок | `trade.html` (журнал заявок), `health.html` | Первый клик медленнее — показывать скелетон |
| Reset workspace / дефолт | Все настраиваемые блоки | Без кнопки сброса пользователь «застревает» в своём расположении |

## 5. Что НЕ копировать (антипаттерны)

1. **Kraken без дефолта.** Отсоединяемые панели хороши только с качественным начальным макетом и
   сбросом. Мы ещё не готовы: у нас нет сохранения настроек — значит, кастомизация создаст хаос.
2. **TWS как эталон сложности.** 20 панелей и workspace-табы привычны профи, но для нашего малого
   набора роботов избыточны: копируем идею «плитки», не количество.
3. **Цвет-binance для подсветки.** Красный/зелёный = направление; если подсвечивать ими «просто
   строку», теряется главная семантика.
4. **Тумблер buy/sell.** Хуже, чем две рядом стоящие формы: пользователь видит только одну сторону.
5. **Heatmap без нейтральной середины.** Пустая белая середина читается как «нет данных», а не «ноль».
6. **«Ещё…» и «Подробнее» без числа.** Скрывают объём и сравнение, нарушают progressive disclosure.
7. **Разные слова для одного состояния** (`active`, `в бою`, `working`, `running`) — ломают фильтры и
   доверие. Один словарь на все 4 раздела.
8. **Сырые технические идентификаторы как главный текст** (`p-base`, `inst:p-base:entry`,
   `6b3b…`) — это внутренний ключ, а не имя, которое читает человек.
9. **JSON в интерфейсе** (`JSON.stringify(r.by_type)`, `JSON.stringify(s.counts)`) — пользователь
   должен видеть «Акции: 12, Фонды: 3», а не скобки.

## 6. Пять конкретных рекомендаций

1. **Ввести единый словарь состояний** на все 4 раздела: `active → «Работает»`, `draft → «Черновик»`,
   `paused → «Пауза»`, `stopped → «Остановлен»`, `archived → «В архиве»`, `PROBLEMS → «Проблемы»`,
   `OK → «Норма»`. Маппинг — на сервере/в общей JS-функции, чтобы не разойтись по шаблонам.
2. **Заменить техшум на подписи в `robots.html`:** убрать `<code>${k}=${v}…</code>` и
   `<code>${st.last_decision}</code>`; вместо этого — «Параметры: 3» с раскрытием по клику и
  человекочитаемое «Решение: держать, позиция 0» рядом со статусом; id оставить мелким вторичным текстом.
3. **Сделать «positions/orders/risk» соседними вкладками в `trade.html`** по образцу Kraken/TWS,
   и добавить закреплённую полосу KPI (депозит, открытая позиция, P&L, число заявок). Риск — отдельный
   блок, не колонка.
4. **В `robots.html` заменить плоский список master-list с сортировкой по тяжести**: сначала
   «Проблемы», затем «Пауза/Остановлен», затем «Работает»; в карточке — причина деградации inline и
   счётчики по типам вместо `JSON.stringify`. В `health.html` — баннер общего статуса и те же ранги.
5. **Применить progressive disclosure с конкретными подписями везде**, где сейчас сырые данные:
   «Показать 12 открытых заявок», «Параметры (3)», «Журнал (48)» — не «Ещё». В `accounts.html`
   заменить `a.status` и `last_decision` на Comparative panel «Портфель vs депозит». Ни одну из этих
   подписей не делать скрывающей сравнение или предупреждение о риске.

## Приложение А: карта шума в наших шаблонах

| Раздел | Пример из кода | Что видит пользователь | Как должно читаться |
|---|---|---|---|
| Роботы | `code=${k}=${v}` в `<code>` | `threshold=0.02 window=5` | «Параметры (2)» → раскрыть |
| Роботы | `JSON.stringify(r.by_type)` | `{"spot":3,"futures":1}` | «Спот 3, фьючерс 1» |
| Роботы | `JSON.stringify(s.counts)` | `{"open":2,"filled":7}` | «Открытых 2, исполнено 7» |
| Роботы | `${st.last_decision}` | `HOLD reason=flat` | «Решение: держать (позиции нет)» |
| Роботы | `${i.spec_id}`, `p-base` | `money_market`, `p-base` | «Денежный рынок», «Бумажный робот №1» |
| Торговля | `o.status`, `last.status`, `slot` | `ORDER_STATUS_NEW`, `slot=3` | «Новая», «Слот 3» |
| Торговля | `inst:p-base:entry` | `inst:p-base:entry` | «Вход, робот p-base» (вторично) |
| Счета | `a.status`, `v.last_decision` | `active`, `HOLD …` | «Активен», «Решение: …» |
| Здоровье | `x.source`, `h.status` | `finam`, `PROBLEMS` | «Финам», «Проблемы» |
| Главная | `h.status === "OK"` | `OK` / `PROBLEMS` | «Норма» / «Проблемы» |

Итог: внешние интерфейсы едины в главном — **позиции, заявки и риск находятся рядом, роботы
показываются уровнями от общего к частному, инструменты группируются по классу, а технические id
живут вторичным текстом**. Наш UI сохранил правильную модель данных, но выставляет её «как есть»;
стоимость исправления — в основном маппинг состояний и замена JSON/raw-строк подписями, без изменения
торговой логики.
