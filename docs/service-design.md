# Сервис роботов и брокеров

Проект архитектуры (23.11.2026). Ничего из описанного не включено в торговый
контур: ворота G2/G3 не пройдены, флаг `FINAM_ALLOW_TRADING=0`.

## 1. Цель и границы

Сейчас логика размазана по скриптам таймеров, а панель только читает файлы.
Нужен единый сервис, который владеет состоянием роботов, счетов и заявок,
предоставляет управление через API и дашборд, и является единственной точкой
входа в брокера.

Сервис отвечает за:
- библиотеку типов роботов и параметры по умолчанию;
- инстансы роботов и их жизненный цикл;
- подключения к брокерам и их валидацию;
- журнал заявок, позиций, решений и аудит действий;
- API для панели и фоновые задачи (расписание, отчёты, сторож).

Сервис **не** отвечает за:
- закрытие сделки по правилам стратегии — это делает стратегия;
- хранение секретов — они остаются в `.env` на сервере;
- изменение модели исполнения без ADR.

## 2. Компоненты

```
web/ (дашборд)  ──HTTP──>  service/ (FastAPI, control plane)
                                 │
                ┌────────────────┼────────────────┐
          robot_library   robot_store        broker_registry
          (spec-ы в коде)  (SQLite)     (FinamAdapter, затем другие)
                                 │
                          execution.py (шлюз заявок)
                                 │
                         раннеры: paper / shadow / live
```

Один процесс FastAPI на WSL (существующий `algotrading-web.service` расширяется),
плюс фоновые воркеры внутри него. Таймеры systemd остаются на первом этапе и
читают настройки из store через API — так бумажный тест не ломается.

## 3. Модель данных (SQLite `infra/db/robots.db`)

| Таблица | Назначение |
|---|---|
| `accounts` | id, название, капитал, потолок экспозиции, лимиты, комментарий |
| `instances` | id, spec_id, инструмент, параметры, режим, статус, счёт, цена исполнения, версия |
| `param_versions` | instance_id, version, params_json, причина, автор, время |
| `instance_events` | аудит всех действий с инстансами |
| `broker_links` | имя адаптера, счёт, статус подключения, последняя проверка (без секретов) |
| `orders` | зеркало `live.csv` в БД для запросов панели |
| `positions` | снимки позиций по счёту и времени |

Секреты и токены — только `.env`; в БД только ссылки на переменные окружения.

## 4. Брокеры-адаптеры

Единый интерфейс `BrokerAdapter`:
- `quote(symbol)`, `account(account)`, `positions(account)`;
- `place_order(request)`, `cancel_order()`, `find_order()`, `order_state()`;
- `check_connection()` — проверка доступности и прав.

`OrderRequest` / `OrderResult` — нейтральные типы, не привязанные к Finam.
`FinamAdapter` оборачивает существующий `FinamBroker` и сохраняет его legacy-
методы, чтобы шлюз `OrderGateway` работал без изменений. Реестр адаптеров
позволит добавить второго брокера, не трогая роботов.

## 5. Библиотека роботов и инстансы

Spec — неизменяемое описание в коде: id стратегии, функция сигнала, параметры
по умолчанию, схема параметров, поддерживаемые инструменты.

Instance — конкретное применение: свой id, spec_id, инструмент, переопределения
параметров, режим (`paper` / `live`), статус, счёт, режим цены, капитал,
экспозиция, тумблер экспирации, версия.

Параметры хранятся версиями. Инстанс активного робота ссылается на одну версию;
редактирование создаёт новую и ставит робота на паузу.

## 6. Жизненный цикл

```
draft → active ⇄ paused → stopping → stopped → archived
```

- `active` — участвует в своём контуре;
- `paused` — виден, решений не принимает, позиция не трогается;
- `stopping` — запрет новых входов, ожидание закрытия по стратегии;
- `stopped` — вышел из контура, может быть перезапущен;
- `archived` — убран с панели, история сохранена.

Физическое удаление запрещено. Перевод `paper → live` — отдельная операция с
проверкой ворот и заполненным счётом; для боя обязательны `account`, `capital`,
`pricing` и явное подтверждение.

## 7. API (основное)

- `GET /api/specs`, `GET /api/specs/{id}` — библиотека;
- `GET/POST /api/instances`, `PATCH /api/instances/{id}`,
- `POST /api/instances/{id}/{start|pause|stop|archive|promote}`,
- `GET /api/instances/{id}/versions`, `/decisions`, `/trades`;
- `GET/POST /api/accounts`, `GET /api/accounts/{id}/reconcile`;
- `GET /api/brokers`, `POST /api/brokers/{name}/check`;
- `GET /api/orders`, `GET /api/positions`, `GET /api/audit`;
- `POST /api/stop` — глобальный STOP;
- `GET /api/health` — состояние сервиса и брокеров.

## 8. Дашборд

Четыре раздела: «Торговля» (KPI, эквити, позиции, тревоги), «Роботы» (таблица
инстансов с действиями), «Библиотека» (spec + мастер создания), «Счета и брокеры».
Детальная страница робота: параметры, версии, решения, сделки, быстрый бэктест
с текущими параметрами, кнопки управления.

Мастер создания: выбор spec → инструмент → параметры (с подсветкой отличий от
дефолта) → режим и счёт → проверка → создание в статусе `draft`.

## 9. Исполнение и расписание

Первый этап: сервис владеет настройками, таймеры systemd по-прежнему запускают
раннеры, которые читают активные инстансы из store. Второй этап: фоновый
планировщик внутри сервиса берёт на себя расписание и отчёты, таймеры убираются.

Каждое решение пишется в журнал с `instance_id` и `version` — это позволяет
честно сравнивать версии параметров на одном окне дат.

## 10. Безопасность

- Глобальные `results/STOP` и `results/STOP_REAL` перекрывают все инстансы.
- Активный live-инстанс без счёта/капитала/режима цены невозможен.
- Правка параметров активного робота автоматически ставит его на паузу.
- Любое изменение — запись в аудит; оптимистическая блокировка по `version`.
- Удаление только через `archived`.
- Панель по-прежнему доступна только из домашней сети.

## 11. Этапы внедрения

1. Фундамент без API и без UI: `BrokerAdapter`, `FinamAdapter`, `robot_store`,
   `robot_library`, тесты. **Текущий этап.**
2. API управления и чтение инстансов панелью.
3. UI: таблица роботов, мастер создания, lifecycle-кнопки.
4. Перевод раннеров на активные инстансы; таймеры остаются.
5. Внутренний планировщик, отказ от systemd-таймеров.

## 12. Что не меняем

Модель исполнения (сигнал по close, сделка по open следующего бара, 0.01% + 1 тик),
существующие `config id` бумажного теста, издержки, STOP-флаги и правила ворот.
Изменения — только отдельными ADR.
