# Журнал заявок и сделок: долгосрочное хранение

## Где пишется

Авторитетное хранилище — SQLite `infra/db/trades.db` (в git не попадает).
`algo/trade_journal.py` — единственная точка записи; `OrderGateway._write()`
(`algo/broker/execution.py`) пишет туда **до** зеркала в CSV.

| Хранилище | Роль | Сколько живёт |
|---|---|---|
| `infra/db/trades.db` | источник правды: заявки, события статусов, исполнения | года (WAL, до миллионов строк) |
| `order_events` | история смены статуса одной заявки | года |
| `trades` | фактические исполнения брокера (если доступны) | года |
| `results/live.csv` | человекочитаемое зеркало для панели и старых скриптов | можно чистить/архивировать |

## Почему не один CSV

* `client_order_id UNIQUE` в БД — идемпотентность за O(1), а не чтение всего файла;
* история статусов: `planned → sent → uncertain/filled` не перезаписывается;
* транзакции и WAL: раннер пишет, панель читает без блокировки;
* бэкап консистентный (`sqlite3.backup()`), а не копия файла на ходу.

## Доступ и бэкап

* `GET /api/journal?limit=100&account=2102993` — последние записи из БД;
* `POST /api/journal/backup` — точечная копия только `trades.db`; полный снимок
  трёх БД делает `./run.sh backup` / таймер `algotrading-backup.timer` (03:00);
* старые строки `results/live.csv` переносятся в БД автоматически при первом
  запуске раннера (`migrate_csv()`, идемпотентно).

## Политика на годы

1. Раз в день автоматически: `algotrading-backup.timer` в 03:00 запускает
   `scripts/95_backup_db.py` три БД; вручную полный снимок — `./run.sh backup`
   (`POST /api/journal/backup` копирует только `trades.db`).
2. Хранить последние 30 ежедневных копий + одну в месяц; копии — вне `results/`.
3. Не удалять `infra/db/trades.db` при деплое: `deploy_wsl.sh` работает по
   whitelist и `*.db` не трогает.
4. При смене сервера — `sqlite3 .backup` на приёмник, не копирование файла
   между активными процессами.

## Суммы и сверка

Денежные поля в `orders` — это **заявка** (цена, лот, номинал), а не фактический
оборот. Фактические исполнения попадают в `trades` из ответа брокера; до тех пор
сверка позиций идёт через `reconcile_guard()` по статусу `sent`.
