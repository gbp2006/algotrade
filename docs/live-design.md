# Архитектура боевого контура (проект «переключатель»)

Состояние на 23.11.2026: **спроектировано и готовится, НЕ включено**. Ни один робот
не переведён в бой. `FINAM_ALLOW_TRADING=0`. Ворота G2/G3 не пройдены.

Принцип: к реальной заявке ведёт один путь, и на нём стоит несколько независимых
замков. Перевод в бой — не правка кода, а заполнение settings-файла на WSL и два
явных действия (`--arm` + env-флаг).

## 1. Источники правды

| Что | Где | Кто меняет |
|---|---|---|
| Реестр роботов и их логика | `algo/configs.py`, `algo/robot_configs.py` | только код, новый id |
| Бумажные решения (целевые позиции) | `results/paper.csv` (WSL), пишет `31_paper_live.py` | таймер, не трогаем |
| Реальные позиции и деньги | Finam API, аккаунт из settings | брокер |
| **Кто из роботов в бою, на каком счету и с какой ценой** | `live_settings.json` на WSL (в git — только `live_settings.example.json`) | пользователь вручную |
| Лимиты, STOP, журнал | `results/live.csv`, `results/STOP*`, `results/live_run.json` | раннер |

`live_settings.json` не деплоится (`deploy_wsl.sh` передаёт только код и docts) и не
коммитится (`.gitignore`). Номера счетов и капиталы остаются на сервере.

## 2. Формат настроек

```json
{
  "defaults": {
    "pricing": "marketable",
    "trade_on_expiry": false,
    "max_exposure": 1.0,
    "max_daily_loss_pct": 0.03,
    "max_qty": 100
  },
  "accounts": {
    "A111111": {"capital": 200000, "comment": "малый счёт G4"},
    "A222222": {"capital": 2000000, "comment": "второй счёт"}
  },
  "robots": {
    "p-base": {"account": "A111111", "pricing": "signal"},
    "u-base": {"account": "A111111"},
    "d20-cn": {"account": "A222222", "pricing": "market"}
  }
}
```

Правила:
- **робот не торгует, пока его нет в `robots`** — белый список, а не чёрный;
- `account` обязан быть в `accounts`;
- `pricing` — один из `signal | marketable | market`;
- `trade_on_expiry` по умолчанию `false` (новые позиции в день экспирации не открываются;
  закрытие существующих разрешено всегда);
- лимиты считаются из `capital` счёта: номинал = capital × max_exposure, дневной
  убыток = capital × max_daily_loss_pct;
- любая ошибка валидации = отказ раннера без отправки заявок.

## 3. Режимы цены (на робота)

| Режим | Что отправляем | Когда уместен | Риск |
|---|---|---|---|
| `signal` | лимитка по цене сигнала из `paper.csv` (как сейчас в тени) | ликвидный инструмент, неспешный вход | может не исполниться |
| `marketable` | лимитка по `ask + 1 тик` (buy) / `bid − 1 тик` (sell), свежий quote | близко к «open + 1 тик» из ADR 18.11 | зависит от свежести котировки |
| `market` | рыночная заявка `ORDER_TYPE_MARKET` | срочный вход/выход | неконтролируемое проскальзывание |

`client_order_id` передаётся для всех трёх режимов — подтверждено по OpenAPI Finam
(`client_order_id` — общее поле PlaceOrder, макс 20 символов). Для `marketable`
котировка старше `max_quote_age_sec` (по умолчанию 60) отклоняется: заявка не уходит,
пишется `rejected`. Молчаливый откат к цене сигнала запрещён.

`signal` и `marketable` — лимитные заявки, цена округляется вверх/вниз до шага
инструмента (`min_step` из `algo/instruments.py`). `market` — без цены; цена в журнале
справочная, для проверки номинала.

## 4. Откуда берём позиции (важно)

Тень считает `delta = target_paper − previous_target_paper`. Для боя этого недостаточно:
если заявка не прошла или была пропущена, модель разъедется с реальным счётом.

Бой считает:

```
target   = сумма target из сегодняшнего paper.csv по всем живым роботам счёта и символа
actual   = позиция брокера по этому счёту и символу
delta    = target − actual
```

Затем дельта неттируется по паре `(счёт, символ)` — если на одном счёте два робота
торгуют одним инструментом, отправляется одна суммарная заявка. Так контур
**сам исправляет** пропуски и отказы на следующий прогон.

Перед заявками каждого счёта — `reconcile_guard`: сверка ожидаемых позиций с
брокером; расхождение выставляет `results/STOP_REAL` и прерывает прогон.

## 5. Экспирация

MOEX: квартальные фьючерсы истекают в **третий четверг** марта/июня/сентября/декабря
(подтверждено moex.com/a7211). Вечный `CNYRUBF@RTSX` экспирации не имеет.

Тумблер `trade_on_expiry`:
- `false` (по умолчанию) — в день экспирации новые/увеличивающие позиции не открываются;
  закрытие и уменьшение выполняются;
- `true` — ограничение снято.

Пропуск пишется в журнал как `skipped` с причиной; следующий прогон пересчитает
дельту от реальной позиции.

## 6. Замки (все должны пропустить заявку)

1. `results/STOP` и `results/STOP_REAL` проверяются перед **каждой** заявкой.
2. Общий lock прогона `results/live_run.lock` (защита от двойного запуска таймером).
3. `OrderGateway`: флаг `FINAM_ALLOW_TRADING=1` **и** явный `--arm` у раннера.
4. `OrderGateway`: per-order lock `results/live.lock`, `client_id` на дубликат,
   лимиты (количество, номинал, дневной убыток), кратность цены шагу.
5. Сверка позиций с брокером перед заявками счёта → STOP при расхождении.
6. Белый список роботов и счетов в settings.
7. Экспирация и свежесть котировки.

Любая заявка пишется в `results/live.csv` со статусом `planned | blocked | rejected |
skipped | sent | uncertain | error` и причиной. Ответ брокера логируется полностью
(ограниченно по длине), `uncertain` никогда не приводит к повторному POST.
