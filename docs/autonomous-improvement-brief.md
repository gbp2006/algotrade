# Бриф длительного автономного исследования и улучшения проекта


> Исторический документ. С 27.11.2026 `FINAM_ALLOW_TRADING`, `--arm` и ARM-тумблеры удалены (ADR в `docs/decisions.md`); актуальная модель — СТАРТ/СТОП/ЗАКРЫТЬ ВСЁ и только счета LIVE.


Версия 1 — 24.11.2026. Живой документ: уточняется по итогам каждой серии
исследований. Это не план «сделать всё сразу», а контракт на повторяемый цикл.

## 1. Цель

Сделать песочницу алготрейдинга **понятным и надёжным инструментом торговли**,
а не набором скриптов: лёгкий интерфейс для реального и бумажного контура,
полный цикл управления роботом, человекочитаемые данные, предсказуемые сбои
и быстрая проверка гипотез.

Критерий успеха цикла: каждое изменение подтверждено тестом,
зафиксировано в ADR/отчёте, выложено на WSL и проверено live-эндпоинтами.

## 2. Жёсткие ограничения (не нарушать)

- Область — **только торговля, роботы, алгоритмы**. Общие/бытовые темы — в
  песочнице `oc`, истории и индексы не смешивать.
- Секреты — только в `auth.json` (600) или `{env:...}`; не выводить в чат,
  логи, отчёты и не копировать в конфиги/деплой.
- На десктопе **не запускать** панель и сервисы роботов. Проверка — через
 bounded curl к WSL, код/тесты/бэктесты — локально.
- Правки для WSL: сначала commit + push, затем `scripts/deploy_wsl.sh --apply --restart`,
  затем проверка `/`, `/trade`, `/robots`, `/accounts`, `/health`, `/api/health`.
- Правки по роботам (панель, таймеры, watchdog, конфиги сервисов) писать и
  проверять на WSL; на десктопе — только код и тесты.
- Модель исполнения (сигнал по close → сделка по open следующего бара,
  0.01% + 1 тик, skip_weekend) меняется **только после ADR**.
- `data/`, `materials/`, `cache/` не читать; тяжёлые данные — только через
  `algo.data.load_cached()`. Вывод скриптов и агентов ≤6 строк сводки,
  детали — в `reports/`.
- Одна сессия — одна тема; завершать записью «Конец:». История — через
  `./infra/db/memory.py brief|lookup|search|outline`, не чтением длинных notes.
- Исследовательские агенты **не меняют код**, не делают коммиты и не выкладывают;
  они пишут только отчёты в `reports/research/`.

## 3. Постоянные треки исследования

### 3.1 GUI и информационная архитектура
- Изучать интерфейсы Kraken Pro, TradingView, OKX, Binance, Finam, Т-Инвестиции,
  Interactive Brokers, OsEngine (BotStation/Tester/Optimizer), а также
 индустриальные дэшборды 2025–2026.
- Искать не «красивые картинки», а решения задач: где живут позиции, как
  показывается риск, как одним взглядом понять состояние 17 роботов, как
  подтверждаются опасные действия.
- Итог: конкретные паттерны с указанием, что применить в нашей панели,
  что не применять и почему.

### 3.2 Логика торговли
- Аудит `algo/live.py`, `algo/risk.py`, `algo/portfolio.py`, `algo/instance_configs.py`,
  `algo/expected.py`, `scripts/31_paper_live.py`, `33_shadow_live.py`,
  `34_live_execute.py`, `35_rollover_live.py`, `40_watchdog.py`.
- Проверять согласованность: версии параметров, лотность, календарь, экспирация,
  пятница, неопределённые заявки, STOP, реконсиляция, идемпотентность.
- Итог: список расхождений с оценкой 영향을 (деньги / ложный STOP / только отчёт).

### 3.3 Скорость и надёжность
- Бюджеты: тёплый `/api/state` < 50 мс, холодный < 700 мс; `/api/health` < 20 мс;
  `/api/accounts/analytics` < 200 мс холодный, < 20 мс кэш; запись заявки
  идемпотентна и не теряет ответ брокера.
- Искать гонки (LOCK, WAL, таймеры 13:55/13:57/14:00), единые точки отказа,
  бесконечные ретраи, утечки памяти, рост БД.
- Итог: таблица «проблема — измерение — решение — как проверить».

### 3.4 Хранение информации
- Источник правды: `infra/db/trades.db` (заявки/сделки), `robots.db` (инстансы,
  версии параметров, рантайм, расписание), `market.db` (бары), `instruments.db`.
  CSV — mirror для человека, не источник правды.
- Проверять схемы, индексы, дублирование, ретенцию, бэкапы, консистентность
  mirror/DB, читаемость отчётов для человека.
- Итог: предложение по схеме/индексам/ретенции/бэкапам без потери истории.

### 3.5 Человекочитаемость
- Инвентарь всего технического, что видит пользователь: raw id (`p-base`,
  `6b3b…`), `ORDER_STATUS_*`, JSON в `response`, stack traces, `code=`, `nan`,
  внутренние имена полей, смешанные единицы.
- Правило: сначала смысл («Заявка исполнена», «Шорт 2 CNY на 49 988 ₽»),
  потом детали по раскрытию. Технический id — второстепенным шрифтом/копированием.
- Группировка инструментов по типу: валютные фьючерсы, индексы, акции,
  сырьё/золото, фонды/паи; внутри — по ликвидности и по счёту. Не смешивать
  MIC-коды и служебные типы вьюхах.
- Итог: таблица «было → стало» и список мест в шаблонах/API.

### 3.6 Тесты и приёмка
- Покрывать критические пути: исполнение заявки, реконсиляция, STOP,
  версии параметров в отчёте, сохранение GUI-состояния, новые API.
- Итог: пропуски, приоритет, минимальный тест для каждого.

## 4. Цикл работы (каждая итерация)

1. Выбрать **одну** тему из треков; завести сессию `sessions/YYYY-MM-DD_HH-MM_slug/`.
2. Собрать факты: код, `results/*.json`, API на WSL, внешние источники.
3. Записать отчёт в `reports/research/` (факты → выводы → рекомендации → проверка).
4. Отобрать 1–3 изменения с высоким соотношением пользы и риска.
5. ADR в `docs/decisions.md` (если меняется модель/данные/API), тесты,
   commit + push, deploy, smoke-проверка страниц и API.
6. Обновить `PROGRESS.md` короткой строкой + ссылкой на отчёт; закрыть сессию
   записью «Конец:».

## 6. Готовый промт для длительной автономной работы (копировать целиком)

> Ты — исследователь и инженер песочницы алготрейдинга. Рабочий каталог
> `/mnt/DiskD/opencode-algo`. Прочитай `PROGRESS.md`, последние 30 записей
> `docs/decisions.md`, `docs/ARCHITECTURE.md` и `docs/autonomous-improvement-brief.md`.
> Тема одной итерации — одна; заведи сессию по `session-workflow` и закрой её
> записью «Конец:».
>
> За одну итерацию:
> 1) выбери один трек из раздела 3 брифа и сформулируй гипотезу;
> 2) собери факты из кода, API песочницы/WSL, отчётов и внешних источников
>    (запросы по-английски, за исключением новостей о России);
> 3) напиши отчёт `reports/research/<тема>.md`: факты, измерение, выводы,
>    рекомендации, как проверить результат; в чат — не более 6 строк;
> 4) предложи 1–3 безопасных изменения с приоритетом. Для выбранных: ADR при
>    изменении модели/данных/API, юнит-тесты, commit + push, `deploy_wsl.sh`,
>    smoke-проверка страниц и `/api/health`, короткая строка в `PROGRESS.md`.
>
> Нельзя: менять модель исполнения без ADR; трогать `FINAM_ALLOW_TRADING`,
> STOP и живые заявки ради эксперимента; читать `data/`, `materials/`, `cache/`;
> печатать или копировать секреты; запускать панель/сервисы на десктопе;
> делать коммиты «на всякий случай» без тестов; смешивать темы в одной сессии.
> Исследования не должны останавливать торговлю: сначала read-only, потом
> proposal, потом изменение с откатом через git.
>
> Особое внимание: human-readable интерфейс, группировка инструментов по
> типу, отсутствие raw id и JSON в пользовательском интерфейсе, честные пустые
> состояния, единая иерархия описаний стратегий/роботов, идемпотентность
> журнала и сверка
> брокера без ложных STOP.

## 7. Метрики, которых держаться

- Tracking error по бумаге — 0 ₽ (порог 200 ₽ в стороже).
- False STOP — 0. Любая сверка, выставившая STOP, разбирается в отчёте.
- Тёплый `/api/state` < 50 мс, `/api/health` < 20 мс.
- Новый API/изменение — минимум один тест и одна строка в results/runs.csv,
  если это прогон/бэктест.
- Каждая найденная проблема — запись в отчёте и либо исправление, либо ADR
  с причиной, почему не исправляем сейчас.
