# Архитектура — единая картина

Канонический документ. Остальные `docs/*-design.md` — детальные спецификации
отдельных подсистем. Здесь фиксируется **что реально работает**, **что подготовлено**,
и **что только спроектировано**. Обновляется вместе с кодом.

> Актуальная модель с 27.11.2026 (ADR в `docs/decisions.md`): панель на порту
> 80, единственный пульт — СТАРТ/СТОП/ЗАКРЫТЬ ВСЁ; виртуальный счёт не торгует;
> `FINAM_ALLOW_TRADING`, `--arm`, ARM-тумблеры и локи заявок удалены. Боевой
> сигнал считается в `algo/live_signal.py` по свежим барам, `paper.csv`
> остался бумажному контуру. Лот везде считается `size_contracts()`; ATR-сайзинг
> и дневной лимит убытка удалены (ADR 27.11/28.11).
> Ниже — частично исторический текст, читать с поправкой на это.

## 1. Одна мысль

Есть стратегии (чистая логика), есть роботы (конкретные настройки стратегий),
есть раннеры (которые превращают сигналы в заявки), и есть единственный шлюз,
через который заявка уходит брокеру. Всё остальное — журналы, панель и предохранители.

```
Код стратегии → Spec → Instance → Runner → OrderGateway → BrokerAdapter → Finam
                    │            │          │              │
                 store        journal    live.csv      .env (секреты)
                    └──────── панель читает / управляет ────────┘
```

Главное правило: **робот торгует, только если он явно включён как активный инстанс
нужного режима**. Всё остальное — подготовка.

## 2. Слои и кто чем владеет

| Слой | Файлы | Что делает | Статус |
|---|---|---|---|
| Стратегии | `algo/strategies/*.py` | чистые сигналы по OHLC | работает, 3 базовые системы + исследовательские |
| Spec (библиотека) | `algo/robot_library.py` | описание типа: параметры, инструменты, дефолты | работает |
| Инстансы | `algo/robot_store.py`, `infra/db/robots.db` | id, spec, параметры, режим, статус, счёт, версия, рантайм | работает; 17 конфигов перенесены |
| Раннеры | `scripts/31…35` | paper / shadow / live / rollover | paper и shadow работают; live и rollover — dry-run |
| Шлюз | `algo/broker/execution.py` | флаг, STOP, лимиты, дубли, lock, журнал | работает; реальная отправка выключена |
| Брокер | `algo/broker/base.py`, `finam_adapter.py` | нейтральный интерфейс + Finam | работает в чтении; заявки не уходят |
| Панель | `web/` | Тест / Торговля / Роботы, API управления | работает |

## 3. Где правда

| Вопрос | Источник правды |
|---|---|
| Какие роботы есть и включены | `infra/db/robots.db`, таблица `instances` |
| Параметры робота | таблица `param_versions`, активная версия инстанса |
| Позиции и equity бумаги | `results/paper.csv` + зеркало `runtime_state` |
| Все намерения заявок и их статусы | `results/live.csv` |
| Бары | `infra/db/market.db` (источник помечен: finam_live / iss / finam_archive) |
| Секреты | `.env` на сервере, никогда в БД и коде |

`CONFIGS` в коде — только семя для первичного заполнения store и история параметров
до первой версии в `configs_at()`; при пустой или недоступной БД бумага и тень не
торгуют по статике (ADR 28.11). `live_settings.json` — миграционный fallback для боя.
Оба являются временными и не должны разрастаться.

## 4. Два контура

**Тест** (`/`): бумажные инстансы, бэктесты, research, QA данных, shadow,
`paper.csv`. STOP — `results/STOP`.

**Торговля** (`/trade`): только live-инстансы, счета и брокеры, `live.csv`,
позиции, перекладка, ворота G3/G4. STOP — `results/STOP_REAL`.

Сравнение бумаги и боя в проект не входит: каждый контур пишет свой журнал,
а расхождения считаются локально по запросу (ADR 28.11). В `/api/health`
остались только проверки живости; защитная сверка модели с брокером — в шлюзе.

Переход из Теста в Торговлю — не переключатель на панели, а отдельное действие
`promote` с заполненным счётом, капиталом и режимом цены. Даже после него заявка
уйдёт только при `FINAM_ALLOW_TRADING=1` **и** `--arm`.

## 5. Что запущено на WSL прямо сейчас

systemd-таймеры: daily 13:55, morning 10:25, friday 18:45, shadow 13:57,
update-live и channel каждые 10 минут. Они запускают скрипты, которые читают
активные инстансы из store. Панель FastAPI на стандартном HTTP-порту 80. Реальных заявок нет.

`algotrading-scheduler.service` работает в режиме `ALGO_SCHEDULER_MODE=robots`:
в `scheduler_jobs` лежат только задания роботов `inst:*`, журнал запусков — в
`scheduler_runs`. Системных заданий в планировщике нет: старые id при старте
удаляются, их исполняют systemd-таймеры. Пользовательские задания без префикса
`inst:` в этом режиме только логируются как `SKIP-SYSTEM` (`log_only`), чтобы не
дублировать таймеры. У заданий есть свои времена, интервалы, таймауты, повторы и
догоняющие реплеи. Режим `off` только логирует всё, `all` исполняет все задания
и дублирует таймеры — последний вариант включается только отдельным решением.
Слово «shadow» относится только к репетиции G3 (`scripts/33_shadow_live.py`).

## 6. Честно о незавершённом

- `34_live_execute.py` и `35_rollover_live.py` готовы и покрыты тестами, но не
  подключены к таймерам и работают только в dry-run.
- Перекладка пока отдельным раннером, не внутри ежедневного решения.
- Планировщик исполняет только задания роботов; системные дублируют systemd-таймеры и логируются (см. §5).
- Ворота G3 (10 дней тени) идут по календарю; их нельзя ускорить кодом.
  G2 упразднён 28.11. Текущая работа — страховка и подготовка переключателя.
- Ряд идей (OsEngine, KZ, RU-01, Rezvyakov) остаётся исследованием: строгие
  гейты не прошли, в контур не добавляются.

## 7. Правила изменений

1. Не менять существующие id инстансов и модель исполнения без ADR.
2. Новый робот — новый id, только после строгой валидации.
3. Правка активного инстанса ставит его на паузу и создаёт версию.
4. Любой прогон пишется в журнал; консоль — одна строка сводки.
5. Сначала тесты, потом деплой на WSL через `scripts/deploy_wsl.sh`.

## 8. Подсистема денежных потоков (добавлена 24.11 без ломки старого)

- Чистые расчёты: `algo/cash_flows.py` (лотность до/после, валидация) и
  `algo/portfolio_metrics.py` (доходность без потоков). Лотность — только
  через `size_contracts()`; каждая таблица чисел в UI — `tabular-nums`.
- Хранение: `algo/cash_flow_store.py` добавляет в `robots.db` три новые таблицы
  (`cash_flows`, `cash_flow_lot_impacts`, `equity_snapshots`) через
  `CREATE TABLE IF NOT EXISTS`. Схема `accounts`/`instances`/`runtime_state`
  не менялась — виртуальные и боевые счета панели работают как прежде.
- Опрос: `algo/account_poller.py` — снимки equity по всем счетам с ключами,
  принудительный `fresh_equity()` перед сделкой (0 лотов при недоступном API),
  подтверждение потока из `GET /v1/accounts/{id}/transactions` Финам только
  по денежным категориям; дельта equity сама по себе потоком не считается.
- Владелец фонового цикла — процесс панели (`ALGO_CASH_POLL_SEC`, по умолчанию
  60 с; полная сверка транзакций раз в 15 циклов). Раннер не пишет дубли.
- API: `web/cash_flows_api.py` добавляет `/api/cash-flows/*` и
  `/api/portfolio/*`; старые ответы `/api/accounts/analytics` и страницы
  сохраняются. Ручное применение денег разрешено только виртуальным роботам,
  для LIVE — только запись обнаруженного брокером потока.
- Адаптеры: `finam` рабочий, `tinvest` зарегистрирован, но без токена и gRPC
  инертен (`NotConfiguredError`); маппинг тикеров — `algo/broker/instrument_map.py`.
- Целевая DDL PostgreSQL/TimescaleDB — `infra/db/schema_timescale.sql` (не применяется
  к текущей SQLite-панели). Офлайн-кэш фронта — Dexie/IndexedDB в
  `webui/src/lib/offline.ts`; темы, плотность и вкладки — `localStorage`.
- Параллельный фронт `webui/` (React 18 + TS strict + Vite + Tailwind/Radix,
  TanStack Query/Zustand, RHF/Zod, lightweight-charts, react-table) работает
  стал основным интерфейсом (старые Jinja-шаблоны удалены): все адреса страниц
  отдают React-сборку, API остаются прежними. Доменные расчёты
  остаются на Python: в TS нет второй формулы лотности. Сборка — `npm run build`
  в `webui/`, тесты — `npm test`. Готовый `webui/dist/` отдаётся тем же сервером
  по `/ui` (ассеты — `/ui/assets`); старые страницы остаются на своих адресах.
  В `scripts/deploy_wsl.sh` добавлены `webui/dist/*` и `webui/dist/assets/*`.
