# Исполнение заявок: состояние G3

Модуль `algo/broker/execution.py` — **каркас безопасности**, не подключён к
живым роботам. `FINAM_ALLOW_TRADING` на сервере остаётся `0`.

## Что уже есть

- `OrderGateway.submit()` перед отправкой проверяет флаг торговли, lock-файл
  `results/live.lock`, повтор `client_id`, лимиты количества/номинала/дневного
  убытка и список разрешённых символов.
- Каждая попытка пишется в `results/live.csv` со статусом `blocked / rejected /
  duplicate / sent / error` и причиной. Ошибка транспорта не теряется, lock
  снимается в `finally`.
- `FinamBroker.place_limit()` формирует лимитную заявку; `_call` уже умеет
  ретраить 429 и обновлять токен после 401.
- `positions_from_response()` + `reconcile()` сверяют позиции модели и брокера;
  неизвестный формат ответа — явная ошибка, а не молчаливое «всё ок».
- Тесты: `tests/test_execution.py` (9) + тест payload'а в `test_broker.py`.
  Реальный API в тестах не вызывается.

## Что осталось до включения флага

1. **Сверить схему заявки с документацией Finam**: поле `clientOrderId` (или
   его аналог), точные названия полей `price`/`quantity`, коды ответов.
   Локальная идемпотентность есть, но серверная — нет.
2. **Репетиция 10 дней** на реальном API с флагом `0`: шлюз пишет `blocked`,
   цепочка расчёта цены и лимитов проверяется без отправки заявок.
3. **Подключить к роботу** новым режимом (не меняя `paper-live`): отдельный
   `live.csv`, сверка позиций перед каждым решением, STOP на расхождении.
4. **Лимиты под реальный капитал** — сейчас значения по умолчанию
   (100 контрактов, 5 млн номинала, 50 тыс. убытка) не являются боевыми.

Ворота и критерии — `docs/live-gates.md`.
