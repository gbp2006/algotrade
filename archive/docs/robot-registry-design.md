# Реестр роботов: библиотека → инстансы → панель → бумага/бой

Концепция пользователя (23.11.2026): робот пишется один раз и попадает в
**библиотеку**; из библиотеки можно создать **столько инстансов, сколько нужно**,
каждый со своими настройками; инстанс можно подключить к бумажной или реальной
торговле, убрать с панели или остановить — без правки кода и перезапуска сервисов.

Документ — проект архитектуры. Ничего из описанного ещё не включено в контур.

## 1. Проблема сегодня

`CONFIGS` и `ROBOT_CONFIGS` — статические списки в коде. Чтобы изменить робота,
нужно править `.py`, коммитить, деплоить на WSL и перезапускать панель. Нельзя
создать второго «Простушку с другими параметрами», временно его выключить или
перевести на другой счёт, не задев остальных.

## 2. Два уровня: Spec и Instance

**Spec (тип робота)** — что умеет робот. Живёт в коде, неизменяемо:
- `id` (`prostushka`, `universal`, `donchian`, `channel_break`);
- python-функция сигнала/исполнения;
- описание, поддерживаемые инструменты, параметры по умолчанию, схема параметров.

**Instance (инстанс)** — конкретное применение типа. Живёт в БД, меняется из панели:
- уникальный `id` (`p-base`, `p-base-fast`, `p-base-2`);
- `spec_id` + переопределения параметров (только отличающиеся от дефолта);
- `instrument`, `mode` (`paper` | `live`), `status`;
- `account`, `pricing`, `capital`, `exposure`, `max_qty`, `trade_on_expiry` — для боя;
- `note`, `created_at`, `updated_at`, `version`.

Один spec → много инстансов. Инстанс одного spec с другими параметрами — новый
id, а не правка существующего.

## 3. Хранение

SQLite `infra/db/robots.db` (рядом с `market.db`, не деплоится):

```
instances(id TEXT PK, spec_id TEXT, instrument TEXT, params_json TEXT,
          mode TEXT, status TEXT, account TEXT, pricing TEXT,
          capital REAL, exposure REAL, max_qty INTEGER,
          trade_on_expiry INTEGER, note TEXT, version INTEGER,
          created_at TEXT, updated_at TEXT)

instance_events(id INTEGER PK, instance_id TEXT, at TEXT, action TEXT,
                before_json TEXT, after_json TEXT, reason TEXT)
```

`instance_events` — append-only аудит: кто/когда/что поменял. Любая правка активного
боевого инстанса пишется сюда и автоматически ставит его на паузу.

Модуль `algo/robot_store.py`: `init_db`, `list_instances`, `get`, `create`, `update`,
`set_status`, `archive`, `history`. Никакой бизнес-логики — только CRUD и валидация.

## 4. Жизненный цикл

```
создан → active ⇄ paused → stopped → archived
```

- `active` — участвует в своём контуре (paper или live);
- `paused` — виден в панели, решений не принимает, позиция не закрывается принудительно;
- `stopped` — то же, но с явным флагом «остановлен вручную», требует явного действия для возврата;
- `archived` — убран с панели, история сохранена, в контурах не участвует.

Удаление физическое запрещено: только `archived`.

## 5. Взаимодействие с контурами

| Контур | Источник инстансов | Правило |
|---|---|---|
| Бумага `31_paper_live.py` | `status=active AND mode=paper` | во время бумажного теста новый инстанс — только с **новым id**; существующие 9 не меняются |
| Тень `33_shadow_live.py` | те же paper-инстансы | без изменений |
| Бой `34_live_execute.py` | `status=active AND mode=live` | заменяет `live_settings.json`; требует account + capital + pricing |

Fallback: если `robots.db` отсутствует, движок работает по статическим `CONFIGS`
как сейчас. Это позволяет внедрять реестр постепенно, не ломая идущий бумажный тест.

## 6. Панель

Новые endpoint-ы:
- `GET /api/specs` — библиотека типов;
- `GET /api/instances` — список с фильтром по mode/status;
- `POST /api/instances` — создать из spec с overrides;
- `PATCH /api/instances/{id}` — изменить параметры/настройки (active live → auto-pause);
- `POST /api/instances/{id}/{start|pause|stop|archive}`;
- `GET /api/instances/{id}/history`.

UI: таблица «Роботы» — столбцы id, тип, инструмент, режим, статус, счёт, P&L,
кнопки «Пауза/Старт/Стоп/Убрать». Кнопка «Добавить» открывает выбор spec и форму
параметров. Изменение активного боя подтверждается отдельно.

Существующие страницы продолжают читать `paper.csv`; реестр добавляется как
новый блок, а не заменяет графики и метрики.

## 7. Безопасность

- Глобальный `results/STOP` и `results/STOP_REAL` действует на все инстансы.
- Инстанс `mode=live` без `account`/`capital`/`pricing` не может быть `active`.
- Перевод paper → live — отдельное действие с записью в `instance_events`.
- Параметры live-инстанса хранятся версиями; откат — новая версия, а не тихая правка.
- Панель без авторизации доступна только из домашней сети (как сейчас) — для
  live-изменений desirable отдельный confirm.

## 8. Порядок внедрения

1. `algo/robot_library.py` + `algo/robot_store.py` + тесты (без UI и без контуров).
2. Panel API + UI управления инстансами; paper-рендер остаётся на статике.
3. `31_paper_live.py` переходит на active paper-инстансы (fallback на CONFIGS).
4. `34_live_execute.py` переходит на active live-инстансы; `live_settings.json`
   остаётся только как миграционный импорт.
5. Индивидуальные расписания инстансов (вход 13:40/13:55, свой таймер).

## 9. Открытые вопросы

- Схема параметров: свободный JSON или жёсткая валидация по spec? Рекомендуется
  минимальная валидация типов + обязательных полей на уровне spec.
- Версионирование: параметры меняются только новой версией инстанса (рекомендуется)
  или in-place с записью в аудит?
- Нужен ли «клон инстанса» как отдельная кнопка (создать копию с новым id)?
- Должен ли `stopped` автоматически закрывать позицию? Рекомендуется нет —
  только запрет новых входов, закрытие по стратегии.
